# Rental Marketplace Product Analytics Platform

An end-to-end product & marketplace analytics platform for a fictional
rental-management product (an Avail/Realtor.com-style business), built to
demonstrate the full analytics stack: synthetic data generation, ELT into a
warehouse, a dbt-style SQL modeling layer, five analyst-grade investigations,
and a 7-page BI dashboard.

## Executive summary

Independent landlords sign up, add properties, publish listings, receive
tenant applications, sign leases, collect rent, and optionally upgrade to a
paid plan. This project answers: **how can the platform acquire more
qualified landlords, improve onboarding and feature adoption, convert more
users to paid plans, retain them longer, and prioritize the most attractive
U.S. markets to expand into?**

## Business problem & stakeholders

| Stakeholder | Question this project answers for them |
|---|---|
| Growth/Marketing | Which channels produce landlords who actually activate, not just sign up? |
| Product | Where exactly do landlords abandon onboarding, and for which segments? |
| Data Science | Does a guided-onboarding experiment actually move activation and paid conversion? |
| Finance/RevOps | What's the MRR trajectory over the next two quarters? |
| Expansion/Sales | Which U.S. metros are the highest-opportunity next markets? |

## Data sources

1. **`market_monthly.csv`** — schema-identical to Realtor.com Economic
   Research's public metro-level inventory/hotness files. **This sandbox has
   no outbound network access**, so this file is generated synthetically
   with realistic trend + seasonality by `src/ingest_realtor_data.py` rather
   than downloaded. Swap in the real CSV from Realtor.com Economic Research
   with one line — see that script's docstring. *If you use the real data,
   attribute it to Realtor.com Economic Research per their terms of use.*
2. **Everything else is 100% synthetic**, generated by
   `src/generate_synthetic_data.py`: landlords, properties, tenants,
   applications, product events, payments, marketing spend, and A/B test
   exposure. Volumes: **50,000 landlords, 150,000 tenants, ~78K properties,
   ~102K applications, ~229K product events, ~275K payments.**

   The synthetic data is not random noise — it encodes intentional,
   documented probability relationships (e.g. mobile signups have lower
   listing-publish follow-through than desktop; landlords who first enable
   online rent collection retain better than those who only use listing
   tools) so that the five analyses below **discover** these patterns from
   aggregated SQL/Python rather than having the conclusions hardcoded. See
   "A data bug I found and fixed" below for how this was verified, not just
   assumed.

### Why SQLite instead of Snowflake, and HTML instead of Power BI

This build runs in a sandboxed environment with **no outbound network
access**, so Snowflake, AWS S3, and Power BI aren't reachable. Every
substitution was chosen to be a drop-in, not a different architecture:

- **SQLite instead of Snowflake.** All SQL in `sql/` is ANSI-compatible —
  CTEs, window functions, conditional aggregation — and runs unmodified on
  SQLite. Porting to real Snowflake is a destination change in
  `src/load_to_snowflake.py` (a `to_snowflake_example()` stub is included),
  not a query rewrite.
- **Local `data/raw/` instead of S3.** Same folder structure/format you'd
  upload to a bucket.
- **A static interactive HTML dashboard instead of a `.pbix` file.** Power
  BI Desktop can't run headless in this sandbox. The dashboard
  (`dashboard/rental_marketplace_dashboard.html`) reproduces all 7 pages
  from the spec with the same charts and drill-downs, built on Chart.js, and
  opens in any browser with no install. `dashboard/data.json` is exported
  directly from the warehouse marts (`src/export_dashboard_data.py`), so
  wiring the real marts into an actual Power BI file later is a data-source
  swap, not a redesign.

## Warehouse model (star schema)

**Staging** (`sql/01_staging/`): typed, deduplicated pass over each raw
source — `stg_landlords`, `stg_events`, `stg_market_monthly`, plus
properties/applications/payments/marketing/experiment staging tables.

**Intermediate** (`sql/02_intermediate/`): `int_user_first_events` (first
occurrence of each event per user, via `MIN() ... GROUP BY`),
`int_funnel_steps` (pivoted funnel timestamps per landlord via conditional
aggregation), `int_subscription_periods` (subscription start/end + monthly
price for MRR math).

**Marts** (`sql/03_marts/`): `mart_executive_kpis`, `mart_landlord_funnel`,
`mart_cohort_retention`, `mart_revenue`, `mart_market_opportunity` — one
mart per dashboard page / analysis.

**Quality tests** (`sql/04_quality_tests/`): primary-key uniqueness, event
sequence logic (can't publish a listing before adding the property, etc.),
and revenue reconciliation between the mart and source.

## The five required analyses (`notebooks/`)

All six notebooks are **real, executed** `.ipynb` files with actual output
cells and embedded chart images — not templates. (`nbformat`/`jupyter`
aren't installable in this offline sandbox, so `src/build_notebook.py` is a
~150-line from-scratch notebook executor: it parses jupytext-style `# %%`
cell markers, runs each code cell in a persistent namespace, and captures
stdout + matplotlib figures as real `.ipynb` outputs. Every number in every
notebook was actually computed, not written by hand.)

1. **`02_funnel_analysis.ipynb`** — Funnel drop-off analysis. Finds that
   **mobile + paid-social landlords abandon between "property added" and
   "listing published" at a 40.9% rate, vs. 1.5% for referral + desktop** —
   the highest-CAC channel is also the weakest at converting mobile signups
   into published listings.
2. **`03_cohort_analysis.ipynb`** — Cohort retention analysis. Landlords
   whose first adopted feature is online rent collection retain at **80.1%
   by month 6, vs. 72.4%** for listing-tools-first landlords.
3. **`04_experiment_analysis.ipynb`** — A/B test (Guided Property
   Onboarding). +6.29pp absolute activation uplift, 95% CI [+3.3%, +9.3%],
   p<0.0001, SRM check passed. **Recommendation: ship.**
4. **`05_revenue_forecasting.ipynb`** — MRR forecast. Holt linear-trend
   model backtested at 2.9% MAPE vs. 39.6% for a seasonal-naive baseline;
   6-month forward forecast included.
5. **`06_market_opportunity.ipynb`** — Market opportunity sizing. Transparent
   40/30/30 (demand/whitespace/performance) weighted score with a
   sensitivity analysis across two alternative weightings.

Plus `01_eda.ipynb` for orientation before the five analyses.

## A data bug I found and fixed (worth reading)

Building this the "right way" — generate data, run SQL, then verify with a
notebook — surfaced two real bugs instead of hiding them:

1. **Funnel analysis initially showed near-zero listing-publish abandonment
   (<1%) across every segment.** That's not a real finding, it's a modeling
   gap: the original generator always published a listing once a property
   was added. I added device/channel-driven publish propensity to
   `generate_synthetic_data.py` and regenerated the full pipeline — the
   funnel analysis above is from the corrected data.
2. **`test_revenue_reconciliation.sql` initially failed by 1,311 landlords**
   (mart said 3,102 active paid landlords; source staging said 4,413). Root
   cause: `mart_revenue`'s subscription-month expansion only unrolled 24
   months, truncating any landlord subscribed longer than 2 years on a
   4-year-old platform. Separately, the pipeline runner's `DROP TABLE`
   idempotency check was silently failing on files with leading SQL
   comments, so fixes weren't even taking effect on reruns. Both are fixed;
   the check now reconciles to a diff of 16 (0.4%, explained by
   month-boundary timing).

Both are documented on the **Data Quality** dashboard page rather than
scrubbed from the history — the quality-test layer's job is to catch this
kind of thing before it reaches a stakeholder.

## How to run this project

```bash
pip install -r requirements.txt --break-system-packages   # if needed

cd src
python3 generate_synthetic_data.py --scale full   # or --scale demo for a fast ~5k-landlord run
python3 ingest_realtor_data.py
python3 load_to_snowflake.py      # builds data/warehouse.db
python3 run_sql_pipeline.py       # staging -> intermediate -> marts
python3 validate_data.py          # data-quality gate
python3 export_dashboard_data.py  # refreshes dashboard/data.json

cd ../notebooks
python3 ../src/build_notebook.py 02_funnel_analysis.py 02_funnel_analysis.ipynb
# (repeat for the other .py -> .ipynb pairs, or open the pre-built .ipynb files directly)
```

Then open `dashboard/rental_marketplace_dashboard.html` in any browser.

## Key findings & recommendations

| Area | Finding | Recommendation |
|---|---|---|
| Acquisition | Mobile + paid-social has 40.9% listing-publish abandonment | Fix mobile property setup before scaling mobile paid-social spend |
| Retention | Rent-collection-first landlords retain 8pp better at month 6 | Nudge new landlords toward rent collection, not just listing publish |
| Experimentation | Guided onboarding: +6.29pp activation, p<0.0001 | Ship to 100% of new landlords |
| Revenue | Holt-trend 6-month MRR forecast; 2.9% backtest MAPE | Use as base-case plan; treat experiment upside as stretch |
| Market | Phoenix, Orlando, Austin, Atlanta rank top-5 under all 3 weightings | Prioritize these for expansion; treat single-weighting-only markets as lower confidence |

## Limitations

- Data is synthetic; relationships were designed to be realistic and
  discoverable, but real-world magnitudes will differ.
- Market data (`market_monthly.csv`) is a schema-identical synthetic
  substitute for Realtor.com's real files due to sandbox network
  restrictions — swap-in instructions are in `src/ingest_realtor_data.py`.
- The forecast uses ~4 years of monthly history, which limits confidence in
  distinguishing seasonality from noise; treat the trend direction as more
  reliable than exact monthly values.
- Cohort retention is capped at a 6-month lookback in `mart_cohort_retention`
  for readability; extending the offset range is a one-line change.
